# P0.5-DOUYIN-GMP-AUTHORIZATION-LIFECYCLE-DESIGN-v1.1

## 1. Design Decision Summary

v1.1 冻结以下设计：

- `bind_status` 与 GMP 授权健康状态继续分离。
- 授权健康状态归属于具体抖音账号。
- 数据库持久化 `UNKNOWN / AUTHORIZED / REAUTH_REQUIRED`，`WARNING` 动态派生。
- 删除账号级 `last_authorization_error_code`，错误码只保留在发送流水。
- 新增 `authorization_version`，解决发送结果与重新授权并发乱序。
- 普通同步、解绑和普通重绑均不得清除 `REAUTH_REQUIRED`。
- 只有“精确账号重新授权确认”可以恢复 `REAUTH_REQUIRED`。
- 首期授权错误只识别已确认的生产事故双条件指纹，不泛化全部 `400`。
- 本地授权阻断生成失败发送流水，但不调用 GMP，也不进入后台重试。
- 页面内预警闭环固定为现有工作台账号徽标、账号横幅和现有重新授权入口。
- 不保存 token、不自动续期、不自动重放历史消息。

被评估但不采用的方案：

| 方案 | 不采用原因 |
|---|---|
| 所有 `code=400` 均判定授权失效 | 会误阻断普通业务错误 |
| 只识别尚未确认路径的 `10010` | 无法覆盖 2026-08-20 实际事故 |
| 使用响应完成时间决定并发新旧 | 完成顺序不等于授权代际 |
| 普通发送成功清除失效状态 | 可能被旧请求的迟到结果错误恢复 |
| 新增账号级错误码字段 | 发送流水已能承担该用途 |

风险等级：`L3`。

## 2. Current State

当前统一链路为：

```text

→ _send_private_message_with_context
→ GMP /send_msg
→ douyin_private_message_sends
```

当前问题：

- [账号模型](E:/work/project/auto_wechat/app/models.py:382)只有绑定状态，没有授权健康投影。
- [统一发送服务](E:/work/project/auto_wechat/app/services/douyin_private_message_send_service.py:101)没有显式接收可信 `merchant_id`。
- [GMP 客户端](E:/work/project/auto_wechat/app/services/douyin_openapi_client.py:181)把所有非零业务码统一归类为 `upstream_business_error`。
- [授权回跳](E:/work/project/auto_wechat/app/routers/douyin_live_check.py:294)使用宽泛同步结果，不能单独作为目标账号恢复证据。
- [空号追问](E:/work/project/auto_wechat/app/services/contact_invalid_followup_service.py:278)会把任意异常放入 60 秒重试。

## 3. Target Architecture

```text
可信调用方身份
  → 统一发送边界按 merchant_id + main_account_id + account_open_id 定位
  → 绑定状态校验
  → GMP 授权健康校验
      ├─ REAUTH_REQUIRED：写失败流水，本地终止
      └─ UNKNOWN/AUTHORIZED/WARNING：调用 GMP
            ├─ 成功：单调更新 last_success_at
            ├─ 事故指纹命中：按授权代际尝试标记失效
            └─ 其他错误：不改变授权状态
```

授权恢复链路：

```text
可信 OAuth state 回跳
→ 前端取得回跳 open_id
→ 现有登录态调用 bind-authorized-open-id
→ RequestContext 提供 merchant_id
→ list_bind_info 精确匹配 main_account_id + open_id + bind_status=1
→ 原子增加 authorization_version
→ 状态恢复为 AUTHORIZED
```

`/auth-redirect` 或普通 `sync-bind-info` 本身不更新授权健康字段。

## 4. Data Model

目标表：`douyin_authorized_accounts`。

| 字段 | PostgreSQL 类型 | 空值/默认值 | 语义 |
|---|---|---|---|
| `authorization_status` | `VARCHAR(32)` | 非空，默认 `UNKNOWN` | 基础授权健康状态 |
| `authorization_version` | `BIGINT` | 非空，默认 `0` | 每次精确授权确认递增 |
| `authorized_at` | `TIMESTAMPTZ` | 可空 | 最近一次精确授权确认时间 |
| `last_success_at` | `TIMESTAMPTZ` | 可空 | 最近一次成功 `send_msg` 时间 |
| `last_authorization_error_at` | `TIMESTAMPTZ` | 可空 | 当前失效证据时间；重新授权后清空 |

约束：

```text
authorization_status IN ('UNKNOWN', 'AUTHORIZED', 'REAUTH_REQUIRED')
authorization_version >= 0
```

字段生命周期：

| 事件 | status | version | authorized_at | last_success_at | error_at |
|---|---|---:|---|---|---|
| 存量迁移 | `UNKNOWN` | 0 | NULL | NULL | NULL |
| 普通绑定同步 | 不变 | 不变 | 不变 | 不变 | 不变 |
| `send_msg` 成功 | `UNKNOWN` 可升为 `AUTHORIZED`；其他不变 | 不变 | 不变 | 单调更新 | 不变 |
| 确认授权失效 | 条件满足时变为 `REAUTH_REQUIRED` | 不变 | 保留 | 保留 | 更新 |
| 精确重新授权 | `AUTHORIZED` | `+1` | 更新 | 保留 | 清空 |
| 解绑/删除 | 全部保留用于审计 | 不变 | 保留 | 保留 | 保留 |
| 普通重绑 | 全部不变 | 不变 | 不变 | 不变 | 不变 |

不新增 `last_authorization_error_code`。账号当前只有一个规范化授权失效结果，发送流水已经保存错误分类，不存在不可替代消费者。

## 5. State Machine

### 有效状态

| 状态 | 条件 | 发送行为 |
|---|---|---|
| `UNKNOWN` | 没有足够健康证据 | 允许发送 |
| `AUTHORIZED` | 存在成功发送或精确授权证据 | 允许发送 |
| `WARNING` | 基础状态为 `AUTHORIZED`，且进入预警窗口 | 允许发送并提醒 |
| `REAUTH_REQUIRED` | 当前授权代际已确认失效 | 本地阻断 |

`bind_status != 1` 的绑定门禁优先级高于上述状态，但不得改写授权健康字段。

### 单调并发规则

发送开始前读取账号的 `authorization_version`，记为 `attempt_version`。

- 成功发送：
  - `last_success_at = max(last_success_at, 当前数据库时间)`。
  - 只允许 `UNKNOWN → AUTHORIZED`。
  - 永远不能执行 `REAUTH_REQUIRED → AUTHORIZED`。
- 授权失败：
  - 仅当数据库当前 `authorization_version == attempt_version` 时写入 `REAUTH_REQUIRED`。
  - 若版本不相等，说明发送期间已完成更新代重新授权；该旧失败不得覆盖新状态。
- 精确重新授权：
  - 原子执行 `authorization_version + 1`。
  - 状态设为 `AUTHORIZED`，更新 `authorized_at`，清空 `last_authorization_error_at`。

因此两种完成顺序均闭合：

| 顺序 | 最终结果 |
|---|---|
| 成功完成后授权失败完成 | `REAUTH_REQUIRED` |
| 授权失败完成后普通成功完成 | 仍为 `REAUTH_REQUIRED` |
| 旧发送失败在重新授权后完成 | 版本不匹配，不覆盖 `AUTHORIZED` |

## 6. Error Handling

### 首期授权失效分类合同

只有同时满足以下条件才分类为授权失效：

1. 接口路径严格等于 `/send_msg`。
2. 上游外层 `code` 规范化后严格等于 `400`。
3. 上游 `msg/message` 经首尾去空格、连续空白折叠后，严格等于：

```text
refresh_token 已过期，需要重新授权
```

不使用子串匹配，不把其他 `400` 判定为授权失效，不依赖尚未确认字段路径中的 `10010`。

后续若取得新的真实结构化证据，应另行审批扩展白名单。

### 规范错误合同

```text
业务码：DOUYIN_GMP_REAUTH_REQUIRED
商户文案：该抖音账号授权已失效，请重新授权后再发送。
动作：reauthorize
HTTP 状态：409
```

人工发送响应固定为：

```json
{
  "detail": {
    "code": "DOUYIN_GMP_REAUTH_REQUIRED",
    "message": "该抖音账号授权已失效，请重新授权后再发送。",
    "action": "reauthorize"
  }
}
```

其他 `400` 继续按普通上游业务错误处理，不更新授权状态。

### 本地阻断与发送流水

账号处于 `REAUTH_REQUIRED` 时：

- 先完成可信账号定位。
- 创建 `status=failed` 的发送流水。
- `error_code=DOUYIN_GMP_REAUTH_REQUIRED`。
- `error_message` 只保存固定安全文案。
- `response_body_json=NULL`。
- 不调用 GMP。
- 不进入 `send_unknown`。
- 不自动重试。

身份定位失败时不创建发送流水、不更新授权状态：

- 人工发送返回现有 `403` 权限错误。
- 后台调用方进入明确失败终态 `douyin_account_scope_mismatch`。
- 禁止尝试按 `account_open_id` 跨商户兜底查找。

## 7. Permission / Isolation

账号唯一定位条件固定为：

```text
可信 merchant_id
+ config.DY_MAIN_ACCOUNT_ID
+ send_context.account_open_id
+ bind_status=1
```

四个调用方的可信身份来源：

| 调用方 | merchant_id 来源 | 定位失败行为 |
|---|---|---|
| 人工发送 | `RequestContext.merchant_id` | HTTP 403，不写流水、不调用 GMP |
| AI 自动回复 | 已持久化 `AiAutoReplyRun.merchant_id` | `failed / douyin_account_scope_mismatch` |
| 回访 | 已持久化 `ReturnVisitRun.merchant_id` | `failed / douyin_account_scope_mismatch` |
| 空号追问 | 已持久化 `ContactInvalidFollowupTask.merchant_id` | `failed / douyin_account_scope_mismatch` |

共享发送函数必须显式接收 `merchant_id`；不得继续在发送后仅凭 `account_open_id` 反查商户。

同一商户多个账号独立维护版本和状态。账号 A 的失效、恢复或预警不得更新账号 B。

重新授权继续要求：

- 一次性可信 OAuth state。
- 登录态 `RequestContext`。
- `auto_wechat:douyin_ai_cs` 权限。
- `main_account_id` 一致。
- `open_id` 精确一致。
- 上游 `bind_status=1`。
- 本地账号不得属于其他商户。

## 8. API Impact

现有字段保持原语义：

```text
authorization_status = authorized / unauthorized / invalid / deleted / not_found
```

新增账号列表字段全部固定返回，不得按状态省略：

| 字段 | 类型 | 空值语义 |
|---|---|---|
| `gmp_authorization_status` | 非空字符串 | `UNKNOWN/AUTHORIZED/WARNING/REAUTH_REQUIRED` |
| `gmp_authorized_at` | RFC 3339 UTC 字符串或 `null` | 尚无精确授权证据 |
| `gmp_last_success_at` | RFC 3339 UTC 字符串或 `null` | 尚无成功发送 |
| `gmp_last_authorization_error_at` | RFC 3339 UTC 字符串或 `null` | 当前没有失效证据 |

禁止新增或返回 token、原始上游错误、`authorization_version`。

`bind-authorized-open-id` 成功响应新增：

```json
{
  "gmp_authorization_status": "AUTHORIZED",
  "gmp_authorized_at": "<RFC3339 UTC>"
}
```

无权限固定保持 HTTP 403，页面显示：

```text
当前账号缺少抖音客服权限
```

模块影响：

| 模块 | 影响 |
|---|---|
| M01 AI 自动回复 | AI 决策不变；发送失效终态为 `failed`，不重试 |
| M01 人工发送 | 409 安全文案，展示重新授权动作 |
| M01 回访 | `failed / douyin_gmp_reauth_required`，不重试 |
| M01 空号追问 | 任务直接 `failed`，不进入 60 秒重试 |
| M02 线索 | webhook、线索入库和分配不变 |
| M04 企业微信 | 无影响 |
| M06 LAS | 无影响 |

## 9. Migration Impact

迁移设计：

- 仅对 `douyin_authorized_accounts` 增加五列及两个检查约束。
- 存量行统一初始化为 `UNKNOWN`，不得根据 `bind_status` 或 `bind_time` 推断健康。
- 所有时间使用 PostgreSQL `TIMESTAMPTZ`，应用映射使用带时区时间。
- 不新增索引；当前读取依赖已有账号唯一约束和商户索引。
- 迁移必须在 PostgreSQL Alembic 唯一 head 上追加；不得使用 `create_all`。
- 旧应用可忽略新增列，因此数据库升级后仍可回滚旧应用。
- 应用回滚时保留新增列和数据，不要求立即执行数据库降级。
- 数据库降级只允许在新应用完全退出后执行；降级会丢失授权投影，必须另行审批。
- 新应用检测不到列或约束时应拒绝启动相关能力，不得静默退回内存状态。

门禁兼容开关设计：

```text
DOUYIN_GMP_AUTH_LOCAL_BLOCK_ENABLED=true
```

- 默认及非法值均按 `true`。
- `false` 只关闭已有 `REAUTH_REQUIRED` 的本地预阻断。
- 发送后的事故分类、状态记录、脱敏和所有原有发送安全门禁仍然有效。
- 该开关不允许启用自动重试或自动补发。

## 11. Risks

- 错误指纹依赖当前生产文本；上游改文案后会漏判，但不会误阻断。
- `authorized_at` 是本系统精确确认时间，不是平台 token 签发或精确到期时间。
- 存量账号没有 `authorized_at`，首期不会产生提前预警。
- 授权版本只解决本系统内并发，不能证明 GMP 内部 token 代际。
- 页面内提醒依赖商户进入工作台，无法替代页面外主动通知。
- 本地阻断开关关闭后会恢复对 GMP 的失败调用压力，只能作为受控兼容回退。
- 发送流水没有 `merchant_id`；本设计依赖发送前的三元账号定位，新增流水商户字段不在本轮范围。

## 12. Open Questions

本版不再把以下事项留给实施阶段临场决定：

- 首期预警阈值固定为精确授权确认后第 23 个完整 UTC 日，即约 30 天窗口的 D-7。
- 计算统一使用 UTC；前端仅按 `Asia/Shanghai` 展示。
- 检测入口固定为账号列表查询和发送前读取，不新增后台定时任务。
- 展示位置固定为现有抖音客服工作台账号徽标，以及当前账号发送区域上方横幅。
- `WARNING` 文案固定为：“该抖音账号授权可能即将到期，建议尽快重新授权，避免消息发送中断。”
- `WARNING` 与 `REAUTH_REQUIRED` 均复用现有授权弹窗，不新建页面。
- 首期不建设短信、邮件、企业微信或 NewCar 页面外通知。
